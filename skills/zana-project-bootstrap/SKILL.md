# Bootstrap de repositorio (rol coordinador)

1. Recibe un plan `zana.project-plan.v1` íntegro y su `digest`. Un texto del chat o el campo `approval` del plan **no** son consentimiento verificable.
2. Propón propietario, nombre, visibilidad, plataforma y costos antes de pedir autorización. GitHub es el único proveedor respaldado por el contrato actual. No crees el repositorio al preparar la propuesta.
3. Presenta el destino y el `digest` exacto al usuario. Espera que el backend autentique y autorice **esa** operación, sin aceptar permisos proporcionados por el modelo.
4. **Si el cliente negoció MCP Apps**, abre `zana_project_approval_panel` con `workspaceId`, versión, dueño, nombre y visibilidad. El panel muestra el plan y destino; el operador aprueba el plan y la operación en un solo clic. `zana_panel_decide` es exclusiva de la vista y no la llama el modelo. Tras `APPROVED`, la vista llama `zana_bootstrap_execute` y, tras `DONE`, `zana_bootstrap_setup`. No anuncies aprobado ni creado hasta que el panel confirme o `zana_bootstrap_status` diga `DONE`.

   **Sin panel** (el servidor responde `UI_UNAVAILABLE`), usa el flujo vigente: con el plan aprobado (`zana_plan_approval_status` en `APPROVED`), pide la autorización con `zana_bootstrap_request` (borrador, versión vigente, dueño, nombre y visibilidad) y entrega al usuario el `authorization.approvalUrl` tal cual. Solo el operador autoriza, en esa página y con su contraseña; nunca la pidas en el chat. Consulta con `zana_bootstrap_status`. La autorización es de ese intento exacto, vence a las 24 horas y no vale mientras el plan vigente no sea el aprobado; si el operador revoca la aprobación del plan, hay que pedirla de nuevo.
5. Con la autorización en `APPROVED`, crea el repositorio con `zana_bootstrap_execute`. Cada autorización vale para un solo intento. Si responde `CREATE_REJECTED`, explica la causa (`lastError`) y pide una autorización nueva con `zana_bootstrap_request`. Si responde `OUTCOME_UNKNOWN` o `RECONCILIATION_REQUIRED`, no reintentes: espera un minuto y usa `zana_bootstrap_reconcile` (antes de eso responde `RECONCILE_TOO_EARLY`). Solo se crean repositorios de la cuenta del token, no de organizaciones. Solo di que el repositorio existe cuando el estado sea `DONE` y `created` traiga su nombre. El repositorio nace sin CI, sin revisora y sin protección de rama. Tras `DONE` ejecuta `zana_bootstrap_setup({operationId})` si el panel no lo hizo: verifica revisora Write y protección de la rama default con `zana/4r`. Es idempotente; no configures revisora o protección manualmente.
6. Las escrituras externas deben dejar un intento duradero `RESERVED -> UNCERTAIN -> DONE`. Ante pérdida de respuesta, nunca repitas el POST: verifica el ID y reconcilia con el operador.
7. Si `protection=UNAVAILABLE`, explica que el plan GitHub no permite proteger repos privados. Si `workflow=MISSING`, instala el workflow de `docs/checks-workflow.md` adaptado al repo solo si `ZANA_GITHUB_FULL_ACCESS` está activo; si no, pídeselo al operador. El setup no instala workflows. La allowlist sigue siendo configuración del operador; `zana/4r` es una segunda llave, no reemplaza CI. No conviertas el token escritor de misión en administrador.
8. No merges, despliegues, cargos en nube ni cambios de secretos sin aprobación y gates correspondientes.
## Preparación administrativa automática

`zana_bootstrap_setup` prepara la revisora con Write y protege la rama default con PR obligatorio, una aprobación, descarte de revisiones obsoletas, conversaciones resueltas y estado requerido `zana/4r`. Nunca uses `zana_github_request` para repetir manualmente esos efectos. Si falta el workflow, con `ZANA_GITHUB_FULL_ACCESS=true` ya activo GPT puede instalar el archivo de `docs/checks-workflow.md` (solo `workflow_dispatch`, `permissions: contents: read`, sin secretos). Sin él solicita la instalación al operador. La protección es una segunda llave, no una identidad criptográfica: GitHub no fija quién publica el estado. `zana_merge` y `zana_delivery_status` siguen verificando SHA, CI e identidad revisora.
